# 2. Git branches – very important

Imagine you're building a TravelEase website.

You have a working version of your project. Now you want to develop a login feature without disturbing the existing code.

Instead of directly modifying `main`, create a new branch.

```
git branch feature-login
```

Switch to it:

```
git switch feature-login
```

Or do both in one command:

```
git switch -c feature-login
```

Now you're working on `feature-login`.

Branch structure

main

Stable project

feature-login

Developing login functionality

After finishing your work:

```
git add .
git commit -m "Added login functionality"
```

Return to main:

```
git switch main
```

Merge your feature:

```
git merge feature-login
```

Now your login functionality is included in `main`.

# 3. Git merge conflicts

This is something you'll encounter in real projects.

Imagine:

- You modify `App.jsx` and change the heading to "Welcome User".
- Your teammate modifies the same line and changes it to "Welcome Admin".
- Both changes are committed on separate branches.

When Git tries to merge them, it may not know which version to keep.

This is called a merge conflict.

Example:

```
<h1>Welcome User</h1>
```

You must manually decide which code to keep.

For example:

```
<h1>Welcome User</h1>
```

Then:

```
git add .
git commit -m "Resolved merge conflict"
```

# 4. Difference between fetch, pull and push

| Command     | What happens                       |
| ----------- | ---------------------------------- |
| `git fetch` | Gets remote updates                |
| `git pull`  | Gets and integrates remote updates |
| `git push`  | Uploads your commits               |

Remember:

- Fetch = Download information.
- Pull = Download + integrate.
- Push = Upload your commits.

# 5. `.gitignore` – extremely important

Suppose you're developing a MERN application.

Your project contains:

```
my-project/
├── node_modules/
├── server/
├── client/
├── .env
├── package.json
└── README.md
```

Should you upload everything to GitHub?

No! Some files should not be uploaded.

Create a file named `.gitignore` in your project root.

Example:

```
node_modules/
.env
.env.local
dist/
build/
.DS_Store
```

What happens?

| File/folder         | Upload to GitHub? |
| ------------------- | ----------------- |
| `node_modules`      | No                |
| `.env`              | No                |
| `package.json`      | Yes               |
| `package-lock.json` | Yes               |
| `src/`              | Yes               |
| `README.md`         | Yes               |

Important: `.gitignore` doesn't automatically stop tracking files that Git already tracks. If `.env` was previously committed, you must remove it from Git tracking and rotate any exposed credentials.

```
git rm --cached .env
git commit -m "Stop tracking environment file"
```

# 6. Undo changes – very useful

Sometimes you modify code accidentally. Git gives you different ways to undo things.

| Command                         | Purpose                                    |
| ------------------------------- | ------------------------------------------ |
| `git restore filename`          | Discard unstaged changes to a file         |
| `git restore --staged filename` | Unstage a file                             |
| `git revert COMMIT_ID`          | Undo a previous commit safely              |
| `git reset --soft HEAD~1`       | Undo last commit but keep changes staged   |
| `git reset --mixed HEAD~1`      | Undo last commit but keep changes unstaged |
| `git reset --hard HEAD~1`       | Remove last commit and discard its changes |



Be careful

`git reset --hard` can permanently discard uncommitted work. Avoid it unless you understand exactly what you're removing.



### Example

You accidentally staged a file:

```
git add .
```

You want to unstage it:

```
git restore --staged filename
```

Your file remains unchanged. Only its staging status changes.

# 7. Git stash – temporarily save unfinished work

Imagine you're developing a login page, but suddenly you need to fix an urgent bug in another branch.

You don't want to commit your unfinished login work yet.

Use:

```
git stash
```

This temporarily saves your tracked working changes and cleans your working tree.

Switch branches:

```
git switch main
```

After finishing your urgent work, return:

```
git switch feature-login
```

Bring back your saved changes:

```
git stash pop
```

Other useful commands:

```
git stash list
git stash apply
git stash drop
```

# 9. Git tags – mark important versions

Suppose your project has reached version 1.0.

You can mark that commit with a tag:

```
git tag v1.0
```

Push the tag:

```
git push origin v1.0
```

Other examples:

```
v1.0  - Initial release
v1.1  - Added login
v1.2  - Added payment
v2.0  - Major update
```

Tags are useful for identifying releases.

# 10. Git configuration

Git needs to know who is making commits.

Set your name:

```
git config --global user.name "Michel"
```

Set your email:

```
git config --global user.email "your-email@gmail.com"
```

Check your configuration:

```
git config --list
```

These details appear in your commit history.

# 13. Real-world workflow for your MERN projects

This is the workflow I recommend following whenever you work on your projects.

When starting work:

```
git pull origin main
```

Create a feature branch:

```
git switch -c feature-authentication
```

After modifying code:

```
git status
git add .
git commit -m "Added authentication"
```

Push your feature branch:

```
git push -u origin feature-authentication
```

Then create a Pull Request on GitHub to merge it into `main`.

For a personal project where you're working directly on `main`, you can simply commit and push without creating a feature branch every time.
